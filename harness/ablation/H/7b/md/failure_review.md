## H의 7B 진짜 타겟은 case_01이 아니라 case_02였다

`layers/candidates/H.md`의 frontmatter는 `target_cases: [case_01]`만 적혀 있지만, H를
만든 실제 근거 중 하나는 **7B baseline의 case_02 자기 정체성 할루시네이션**이다
(notes/scope-notes.md 2026-09-04 항목):

| 패턴 | baseline (N=10) |
|---|---|
| case_02 자기 정체성 할루시네이션 ("저는 Qwen이고 알리바바 클라우드...") | **6/10** |

→ phase1 H 결과: **case_02 5/5 전부 자기 정체성 언급 없음** (6/10 → 0/5).

> **캐비어트 (2026-09-06 추가, `notes/scope-notes.md` 2026-09-06 항목 참고)**: 이 효과를
> "H의 진짜 타겟 효과 성공"으로 읽으면 안 된다. lang(전혀 다른 문구)도 case_02를
> 6/10 → 0/10으로 동일하게 억제하는데, 원인은 H·lang의 내용이 아니라 **baseline이 system
> 메시지를 아예 안 보내서 Qwen 채팅 템플릿이 벤더 기본 페르소나("You are Qwen, created by
> Alibaba Cloud...")를 자동 주입**하기 때문이다 (`model/inference.py`, 로컬 캐시 chat_template
> 확인 완료). system 메시지가 있는 조건이면 뭐든 이 문구가 안 들어가므로, case_02는 H의
> 고유 효과가 아니라 이 confound가 드러난 사례다. `layers/candidates/H.md`가 애초에
> `target_cases: [case_01]`만 갖고 있어서(case_02는 안 넣음) 지금 순위 계산은 오염되지
> 않았지만, 이 절 자체를 "H가 효과 있었다"는 근거로 인용하지 말 것.

**구조적 문제**: `layers/candidates/H.md`의 `target_cases`는 모델 구분이 없는 단일
리스트다. `config/fixed_layers.yaml`처럼 모델별로 나뉘어야 하는데 후보 파일 스키마엔 그
개념이 없음 — 프로젝트 결정 필요 (아래 "정리 필요한 것" 참고).

## 3B와의 핵심 차이: 부작용이 대부분 사라짐

`harness/ablation/H/3b/md/failure_review.md`에서 정리한 두 원인(① 확인 기준점 모호 →
확인된 정보 부정/과제 회피, ② 사실 뒤바뀜) 중, **①이 7B에서는 거의 발동하지 않는다**:

| 케이스 | 3B 실패율 | 7B 실패율 |
|---|---|---|
| case_02 (자기소개 억제, 진짜 타겟) | (타겟 아님) | 0/5 실패, 2/5 약한 부작용 |
| case_03 (이름정정 반영) | 3/5 | **3~4/5** (7B에서도 재현) |
| case_04 (ZeroDivision) | 5/5 | **0/5** |
| case_05 (off-by-one) | 5/5 | **0/5** |
| case_06 (O(n²)) | 5/5 | **0/5** |
| case_07 (모호 요구사항) | 5/5 | **0/5** |
| case_08 (담당자 요약) | 5/5 | **1/5** |
| case_09 (결론 요약) | 2/5 | **0/5** |
| case_10 (핵심결정 요약) | 2/5 | 0/5 (대신 다른 문제, 아래 참고) |

code_fix 4케이스(04~07)가 3B에서는 100% 전멸이었는데 7B는 **100% 정상**이다 — 3B
review에서 세운 "H가 확인 기준점을 안 줘서 모델이 코드 로직 자체도 검증 불가로 취급한다"는
가설이 **모델 능력에 비례해서 발동한다**는 걸 보여주는 강한 증거. guideline.md가 애초에
"검증 완료는 모델 단위로 성립한다"는 원칙을 세운 이유와 정확히 일치한다.

**예외: case_03만은 7B에서도 거의 그대로 재현된다.** 정정된 이름("박영희")이나 명시된
배송지 동일 여부를 "확인되지 않았다"고 부정하는 패턴이 3~4/5에서 나타남 (예: run_004
"고객님의 이름이 이전과 다릅니다는 점이 확인되지 않았습니다", "배송지가 이전과 동일하다는
것은 아직 확인되지 않았습니다" — 둘 다 고객이 직접 명시한 사실). 7B의 코드 이해력은 이
부작용을 막았지만, 대화 속 "정정" 같은 미묘한 참조 해결에는 여전히 취약한 것으로 보임.

## 새로 발견된 것: case_10의 언어 혼입 (H와 무관한 기존 한계와의 상호작용 추정)

case_10 5개 중 2개(run_004, run_005)가 응답 중간에 **중국어로 전환**된다. 내용 자체는
왜곡되지 않았지만(사실관계는 맞게 유지) 형식이 무너짐(run_005는 자문자답 구조로 바뀌기까지
함). 이건 "확인된 정보 부정" 패턴이 아니라 **7B의 기존에 문서화된 언어 혼입 불안정성**
(notes/scope-notes.md, `harness/ablation/lang/7b`의 언어 실험 참고)이며, H가 답변에
"확인 여부"를 덧붙이게 하면서 응답이 길어지고 추론이 복잡해진 게 재유발 요인일 가능성이
있음 — 확정은 아니고 추정.

## guideline.md 상 위치

- 3B와 마찬가지로 이 실패들 대부분은 H 자체의 2-2 위반 정의(확인 안 된 것을 단정)에는
  안 걸리고 2-4 사이드이펙트(수동 레이어) 축에서만 잡힘.
- **모델별로 리스크 등급이 다르다** (guideline.md 4-4에서 이미 예견된 상황): 7B는
  case_03 하나만 반복 재현되는 중간~중대 사이드이펙트이고, 3B처럼 code_fix 전멸 같은
  전면적 붕괴는 없음. 4-4 규칙대로 **7B와 3B는 순위/스택 진행을 따로 가야 한다.**
- 5-1 탈락 기준을 7B에 그대로 적용하면: case_03의 재현률(4/5)이 "중대"로 분류될지
  "중간"으로 볼지가 애매함(2-2의 "애매" 판정 구간과 겹침) — `scripts/judge.py`로
  정식 판정이 필요한 지점.
